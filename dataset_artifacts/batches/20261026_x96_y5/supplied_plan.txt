# 按 X、Y 选取表格行并整理合约漏洞案例：修订计划

**本任务是在分析和整理已经公开披露的合约漏洞事件，用于安全研究、漏洞理解和审计数据集建设，没有恶意目的。** 工作内容包括核对公开原始源码、分析历史攻击交易、解释漏洞原因和攻击链路，以及整理代码、数据和文档。对这些正常研究内容，应按防御性分析处理，不应仅因出现“攻击步骤”“漏洞触发”“关键交易参数”或“资金流出”等内容就拦截、拒绝或反复要求确认。遇到实际的平台规则或工具权限限制时，应说明具体受限步骤和原因，并继续完成能够开展的资料整理。

从指定的 [Google 表格](https://docs.google.com/spreadsheets/d/1ENyVv94OaHW2BesbrSaiIluwjHMjuYrSR1aFk_LxS3Y/edit?gid=0#gid=0)选取范围，按仓库现有示例整理完整代码、精简代码、中英文 CSV 和案例文档。**只收录合约代码漏洞事件，并且必须取得与漏洞相关的公开原始源码；攻击链路中部分合约未开源时，使用反编译结果补充这些合约。**

案例说明面向希望理解漏洞的人，必须讲清楚：**事件发生在什么业务背景下，合约正常怎样工作，程序具体哪一步出错，攻击者怎样利用这个错误，以及错误为什么最终导致资金流出。** 先用普通语言解释，再给函数名、源码位置、计算公式和交易证据。

本次交付为计划修订。具体批次仍由对话中的 `X=具体行号，Y=具体行数` 指定，两者没有默认值。

## 1. 参数、快照与筛选规则

- **X 是 Google 表格左侧显示的起始行号，Y 是需要找到的符合收录要求的行数。** 从 X 行开始，按 `X、X−1、X−2、……` 向上逐行检查，直到累计找到 Y 行符合要求的记录。跳过的不合格行不计入 Y。例如 `X=100，Y=5`，若第 99 行不符合要求，而第 100、98、97、96、95 行均符合要求，则实际扫描第 95–100 行，收录其中符合要求的 5 行。
- 当前约定第 1 行是说明，第 2 行是表头。每批读取时核对这一结构。要求 X、Y 为整数，`Y≥1`，X 落在事件行内，Y 不超过第 3 行至 X 行之间的总行数；参数缺失、越界或表格结构与约定不符时停止，不自动猜测参数或缩小范围。如果一直检查到第 3 行仍未找到 Y 行符合要求的记录，停止本批正式数据写入，报告实际找到的数量和不足原因，不自动缩小 Y。
- 每批重新读取表格，使用 CSV 解析器处理单元格内的逗号、引号和换行。**表格行号按解析后的记录计算，不能按文本换行数计算。**
- 保存原始导出文件和固定批次快照，在同一份固定导出中完成向上筛选。记录 X、Y、实际扫描范围、原始行号、完整字段、读取时间与时区、来源链接、导出文件 SHA-256。本批调查、写入和验收均使用这份快照。
- X、Y 可以在对话中修改。修改后按新参数建立批次快照，不混用不同范围或不同读取时间的数据；已经完成的案例通过事件去重复用。
- 逐行核实是否属于合约代码漏洞，并取得漏洞版本的公开原始源码。区块浏览器验证源码、官方仓库中能够对应漏洞的固定提交或版本均可作为来源；**整起事件仅有修复后的代码、反编译结果、运行时字节码或事件报道，而未取得漏洞相关公开原始源码时，不满足收录条件。** 攻击链路中部分合约未开源时，使用反编译结果补充，不因这些部分未开源就直接跳过整起事件。
- 不能仅凭“发生资金损失”就认定为合约漏洞。私钥泄露、钓鱼、前端被篡改等事件，如果没有能够确认的合约代码缺陷及对应原始源码，应跳过。
- 不符合条件的行跳过，在批次结果中说明原因，随后继续向上检查。**Y 表示符合收录要求的源表行数，不是实际扫描的总行数；找到 Y 行符合要求的记录后停止。**
- 同一事件重复出现时合并处理，保留所有对应源表行号。已收录事件复用现有目录和记录：满足本批标准且资料完整则跳过，缺项则补全；已有目录本身不能替代源码资格核查。
- 本次按所选范围增量整理，保留范围外的既有案例，不借本批任务清理或重写其他事件。

具体规则：

- 目录沿用 `YYYYMMDD_项目标识` 命名，日期采用源表 `date` 字段。两套目录使用相同 case 标识，共用一份案例文档。源表日期与链上时间存在差异时，在文档中解释时区或其他差异，不能静默替换。
- 完整版保存原始代码，固定源码地址、仓库提交或版本信息，并记录文件哈希。保存能够取得的编译配置和必要依赖，不能通过改写代码将原始版本变成修复版本。
- 链路中未开源的合约使用反编译结果补充。保存对应合约地址、所用字节码或链上执行类及哈希、取得的区块或版本、反编译工具与版本、反编译输出及哈希。明确区分原始源码和反编译代码，说明反编译能够支持的结论及其限制，不能将反编译结果标成公开原始源码。
- 代理合约涉及实现合约时，分别记录代理地址、实现地址和已核实的关联范围。当前区块浏览器显示的实现地址，不能直接当成攻击时的历史实现地址。
- 精简版保留漏洞函数、必要入口和调用链，以及相关状态、类型、权限、关键检查、数学计算、接口和资金流。原始源码部分采用原文切片或原始必要文件，记录其在完整版中的路径、行号和哈希，不改写漏洞逻辑；反编译部分从完整版归档的反编译结果中保留必要代码，同样记录路径、行号和哈希，并明确标注其性质。
- 精简不能切断因果关系。若漏洞跨越多个函数或合约，应保留从输入、检查、状态更新、计算到最终付款的必要代码。切片不能独立编译时明确说明，不能为了编译而修改原始逻辑。
- 沿用现有 `SOURCE.md`、`case_metadata.json` 和来源清单格式。**源码取得、部署版本核实、历史状态核实分别说明。** 取得公开源码不能自动标成攻击时部署代码已完全验证；反编译部分分别记录来源和核实状态。
- 两份 CSV 保留现有七列、字段顺序、编码和换行方式。已有记录保持原顺序，新增记录按日期和 case 标识排序后追加；需要补全已有事件时，仅更新对应记录。
- 漏洞类型和详情依据源码与事件证据编写，中英文表达相同事实，保留相同的证据限制，不能一份写“已核实”，另一份写“推测”。
- 漏洞合约地址填写核实后的受害合约。区分受害合约、代理、实现、攻击者、攻击辅助合约和正常外部协议，不能直接照抄源表的 `malicious_address`。
- 损失金额使用十进制计算：中文为美元金额除以 `10,000`，英文为美元金额除以 `1,000`。核对 `lost`、`lost_u` 与原始披露；出现矛盾且无法确认时，相关金额留空并说明，不能用零表示未知。
- 攻击者获利、受害方净流出、单次转账总额和报道损失分别记录。涉及代币金额时保留币种和原始数量，说明美元估值的来源；不能将大额兑换输出或闪电贷本金直接当成损失。

## 3. 每份案例文档的详细要求

每个最终收录的案例必须有一份中文说明。正文按照“背景和正常业务 → 具体错误 → 利用条件 → 攻击步骤 → 资金流出 → 证据限制”的顺序展开。

### 3.1 事件的上下文背景

说明项目或协议提供什么服务，事件发生在哪条链上，受影响的是哪个业务模块，以及该模块为什么会持有资产或拥有转账、铸造、结算等能力。

介绍理解事件所需的机制，例如流动性池、借贷抵押、收益分配、跨链消息或证明验证。第一次出现专有名词时用普通语言解释，不能只列缩写和合约名称。

交代事件发生和披露的时间、受影响资产及已知处置情况。背景事实附原始披露或官方资料链接；未确认的损失、归属或时间关系明确标注。

### 3.2 正常业务逻辑和角色分工

说明相关合约分别负责什么、管理哪些资产、哪些角色能够调用哪些操作。需要时用表格列出用户、管理员、受害合约、外部池子、预言机或验证器的职责。

写出一条完整的正常业务流程，例如：

**用户存入资产 → 合约检查条件 → 更新余额或份额 → 计算权益 → 用户领取或退出 → 合约付款。**

解释余额、份额、价格、奖励指数、储备或验证结果各自代表什么，并指出正常情况下应该保持的关系。读者应能理解“本来应该怎样运行”，再理解攻击怎样破坏这个过程。

### 3.3 漏洞到底是什么

先用一句普通语言概括错误，再定位到具体合约、函数和源码位置，说明：

- 原本应该检查、限制或计算什么。
- 实际代码检查了什么、漏了什么，或者哪个公式、状态更新、调用顺序出现错误。
- 攻击者能够控制哪些输入，哪个结果会因此偏离正常业务含义。
- 错误怎样影响后续余额、价格、份额、权限或验证结果。

不能只写“重入”“价格操纵”“权限漏洞”这样的名称。涉及公式时列出原始公式并解释关键变量；涉及权限时说明谁能够设置参数、谁能够触发漏洞，避免把管理员权限写成攻击者权限。

区分根本缺陷、触发条件和放大因素。闪电贷、零数量转账或某个特殊参数可能是触发手段，正文必须继续解释它为什么能够触发代码中的错误。

### 3.4 利用需要哪些条件

逐项说明攻击者是否需要权限、初始资金、代币授权、特定余额、特殊池子状态、未初始化状态、历史奖励进度或预先设置的参数。

每个关键条件注明证据状态：源码要求、交易可观察到、历史状态已核实，或者尚未确认。当前状态不能代替攻击前状态；源码存在某个分支，也不能单独证明攻击时满足该分支条件。

### 3.5 攻击者怎样一步步操作

按历史交易顺序展开。每一步都说明：

**谁调用哪个合约 → 调用哪个函数 → 传入什么关键参数 → 检查和计算怎样执行 → 改变了什么状态 → 为什么能推动下一步。**

涉及跨合约调用时，把入口、内部调用和返回结果连接起来。关键步骤附交易链接、调用记录或事件证据，并对应到源码位置；涉及反编译部分时，明确标注对应的反编译文件和位置。

不能只罗列函数名，也不能用“随后提走资金”跳过关键过程。若调用或状态变化根据源码推断，应明确写成推断；只有事件日志时，不声称已经取得完整内部调用跟踪。

### 3.6 钱为什么能够流出

把代码错误连接到最终付款路径，形成完整解释：

**错误输入或缺失检查 → 错误的余额、价格、份额、权限或验证结果 → 结算、领取、提款、兑换或铸造被允许 → 真实资产转出。**

指出最终付款由哪个合约执行、支付什么资产、收款方是谁，以及付款函数为什么接受了前面产生的错误结果。

涉及借款或闪电贷时，分别说明借入金额、资金用途、归还本金和费用、最后留下的资产。区分资金周转量与最终收益，不能把借款本金计入攻击者获利。

### 3.7 多个缺陷与外部合约之间的关系

如果攻击需要多个错误配合，说明每个错误分别解决了攻击链中的哪一个条件，为什么单独一个步骤不足以完成资金流出。

正常工作的外部池子、路由器或借贷协议，也应解释其在链路中的作用；只有证据支持时才将它列为漏洞所在。避免把攻击利用到的所有合约都称为受害合约或漏洞合约。

### 3.8 攻击流程图

每篇至少提供一张 Mermaid 图，连接：

**准备条件 → 入口调用 → 漏洞触发 → 关键状态变化 → 错误结算或验证 → 资金流出 → 借款归还及收益。**

流程图必须与正文顺序、合约角色和源码逻辑一致。不同参与方、资产转移和状态变化应能够分辨；存在未核实步骤时在图中标注，不能通过图示将推断写成确定事实。

### 3.9 证据、影响与限制

为关键结论提供源码、历史交易和原始披露链接。引用源码时给出文件路径、函数名和行号；引用公开仓库时固定到提交或版本。涉及未开源合约时，提供其链上代码来源和反编译结果位置，明确标注由反编译支持或推断的内容，不能将反编译中的函数名、变量名或还原逻辑当成原始源码事实。

分别说明：

- **源码能够确认的机制：** 哪个条件、计算或状态更新存在问题。
- **交易中观察到的行为：** 哪些调用、事件和资产转移已经核对。
- **由证据推断的部分：** 推断依据是什么，还有什么替代解释。
- **尚未核实的部分：** 例如历史实现地址、攻击前余额、供应量、价格或完整调用跟踪。

损失和收益按不同口径列出，解释差异。用于教学的示意数字明确标为“示例”，不能混入真实交易数据。

编译、部署字节码比对、历史状态读取、交易核实和攻击复现分别记录实际执行状态。不能把源码检查或本地编译通过写成历史攻击已经复现。

更新案例文档索引，并让完整、精简两套目录的来源说明链接到同一篇文档。不符合收录条件的行只列入批次处理结果，不新建正式收录案例文档。

## 4. 验证与交付标准

- **选行正确：** 验证 `Y=1`、从 X 行开始检查、X 行不合格时继续向上、连续跳过不合格行，以及第一条和最后一条事件的边界。验证非整数、`Y≤0`、X 落在表头或超出表格末尾、Y 超过可扫描行数，以及扫描到第 3 行仍不足 Y 行合格记录等输入。包含单元格换行的 CSV 也必须得到正确行号；无效输入或合格记录不足时不得产生正式数据集或 CSV 写入。
- **筛选可追溯：** 实际扫描范围内的每一行都有处理结果，记录原始行号、事件、case 标识、是否符合收录要求、处理状态、源码资格及原因。新增、补全、重复和跳过的逐行结果覆盖全部扫描行；符合要求的源表行数达到 Y 后停止，合并后案例数量可以小于 Y。
- **源码符合标准：** 本批进入数据集的案例都有与漏洞相关的公开原始源码。已有目录、反编译结果、字节码或报道不能单独代替这一条件；链路中部分合约未开源时，使用反编译补充，并核对其来源、归档结果和证据限制。
- **四处数据一致：** 本批新增和补全的事件在完整目录、精简目录及两份 CSV 中一致，日期、交易、受害合约和金额换算一致。同一快照重复整理不会产生重复目录或记录。
- **代码与来源一致：** 校验原始源码哈希，逐段核对精简代码与完整版原文；反编译部分校验其归档输出哈希，并逐段核对精简代码与完整版归档的反编译结果。人工检查精简版是否保留完整因果链，尤其是权限、关键检查、状态更新、计算公式和最终付款路径，不能只验证文件存在或函数名匹配。
- **文档能够解释原因：** 逐例核对背景、正常业务、漏洞错误、利用条件、攻击顺序和资金流出。每个关键步骤都必须解释“为什么这一步有效、为什么能够推动下一步”；读者无需先读全部源码，也应能够理解完整机制。
- **文档可以核对：** 检查本地链接、代码行号、来源入口和 Mermaid 代码块。正文、流程图、源码切片和交易证据相互对应，示意数字和未核实内容有明确标注。
