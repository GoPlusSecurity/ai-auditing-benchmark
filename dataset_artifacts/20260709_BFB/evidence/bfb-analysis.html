BFB Token Exploit Analysis

Date: 2026-07-08

Loss Estimate: 350.616633079707222431 WBNB, approximately $197,817 at the in-transaction WBNB oracle price of $564.19734001.

I. Executive Summary

  • Verdict: Confirmed Exploit - zero-value transfer side-effect / deflationary AMM-reserve manipulation.
  • Root Cause: The vulnerable BFBToken contract at 0x719699762fFCC7AadBdCec4E7cf03569E5e99999 lets transferFrom(..., amount=0) enter _transfer() and execute _priceDeflPool() side effects. That side-effect can burn BFB directly out of the Pancake BFB/WBNB pair and call sync() even though no BFB was actually transferred. The attacker repeatedly manipulated the pair price, invoked zero-value EOA-to-EOA transfers to burn pair BFB, then swapped tiny BFB amounts for WBNB until the pair lost 350.616633079707222431 WBNB.

II. Vulnerability

A. Business Logic Context

BFB is a deflationary token with automated pool maintenance. Its _priceDeflPool() routine checks the token price from the Pancake BFB/WBNB pair and, if the price has fallen enough and both from and to are externally owned accounts, burns a percentage of the pair's BFB balance and calls sync() on the pair.

That design makes token transfers mutate AMM reserves. The intended invariant should be that a zero-value ERC-20 transfer is a no-op for balances and cannot change third-party pool reserves.

B. The Vulnerability

// Contract.sol, BFBToken at 0x719699762fFCC7AadBdCec4E7cf03569E5e99999
function transferFrom(address from, address to, uint256 amount) public override returns (bool) {
    require(balanceOf[from] >= amount, 'balance error');
    require(allowance[from][msg.sender] >= amount, 'approve error');
    allowance[from][msg.sender] -= amount;
    _transfer(from, to, amount);
    return true;
}

function _transfer(address from, address to, uint256 amount) private {
    require(from != address(0), 'from error');
    require(to != address(0), 'to error');
    _transferRoot(from, to, amount);
    _priceDeflPool(from, to);
    _deflPool(from, to);
    _bound(from, to, amount);
}

function _priceDeflPool(address from, address to) private {
    uint256 nowPrice = _getTokenPrice();
    if(nowPrice == 0) return;
    if(nowPrice >= fallLastPrice) {
        fallLastPrice = nowPrice;
        fallLastTime = block.timestamp;
        return;
    }
    if(fallLastPrice > nowPrice * (DENOMINATOR + fallPriceRatio) / DENOMINATOR && !isContract(from) && !isContract(to)) {
        uint256 burnAmount = balanceOf[WBNB_Token_LP_Address] * fallPriceBurnRatio / DENOMINATOR;
        _transferRoot(WBNB_Token_LP_Address, address(0), burnAmount);
        IUniswapV2Pair(WBNB_Token_LP_Address).sync();
        fallLastPrice = _getTokenPrice();
        fallLastTime = block.timestamp;
    }
}

The bug is the missing amount > 0 guard before invoking transfer side effects. With amount=0, both balance and allowance checks trivially pass, but _priceDeflPool() can still burn BFB from the pair and rewrite AMM reserves.

C. Why It Was Exploitable

The attacker used an EOA as both from and to, satisfying !isContract(from) && !isContract(to), while the attack contract performed the calls. After each small BFB-to-WBNB swap pushed the BFB price down, a zero-value transferFrom(attacker, attacker, 0) triggered PriceDeflPool, burned BFB from the pair, and synced the manipulated reserves. This made repeated tiny BFB sales pay out large amounts of WBNB.

III. Technical Attack Flow

  1. The EOA 0x3BFA85127C9871D3f74c30e36A618a77f0aE6b0F called attack contract 0xDd868618956418f77d922FA5D42960fb5FB01b7B with selector 0xdbee9970.
  2. The attack contract called BFB.transferFrom(attacker, attackContract, 0) and later repeatedly called BFB.transferFrom(attacker, attacker, 0). The trace shows multiple zero-value Transfer logs followed by PriceDeflPool burns from the Pancake pair.
  3. The attack contract borrowed temporary capital: a DODO-style flash loan from 0x8F73b65B4caAf64FBA2aF91cC5D4a2A1318E5D8C, Venus mint/borrow actions using vBTC 0x882C173bC7Ff3b7786CA16dfeD3DFFfb9Ee7847B, and a WBNB borrow from Venus market 0x6bCa74586218dB34cdB402295796b79663d816e9. These venues had no final balance loss.
  4. The attacker used borrowed WBNB to buy BFB from the Pancake pair, then entered a repeated loop: sell a small BFB amount for WBNB, call zero-value transferFrom, trigger PriceDeflPool, burn pair BFB, sync, and sell again.
  5. Final balance changes show the Pancake BFB/WBNB pair 0xffB43C8A00A47B737d27b2aE59A35e269A21d040 lost exactly 350.616633079707222431 WBNB, while the attacker EOA gained the same WBNB amount before gas.
