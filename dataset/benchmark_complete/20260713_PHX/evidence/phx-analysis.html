PHX Pair Burn Exploit Analysis

Date: 2026-07-12

Loss Estimate: 156.205683367 WBNB (~$89,532 at the on-chain WBNB oracle price observed in the transaction)

I. Executive Summary

  • Verdict: Confirmed Exploit - AMM reserve manipulation through token-side pair burning.
  • Root Cause: The PHX token at 0x2540CDc3317Aa614178c29e2a1C7d5cDcEBBa481 burns PHX directly from its Pancake PHX/WBNB pair during _takeSellFee() and immediately calls pair.sync(). The attacker first used borrowed WBNB to buy most PHX out of the pair, then triggered the sell-fee path so the pair's PHX reserve was synced down to 1,000,000 raw units while WBNB remained high. A direct pair swap then treated a ~504.474 PHX transfer as enough input to withdraw almost all WBNB liquidity.

II. Vulnerability

A. Business Logic Context

PHX is a fee-on-transfer ERC-20 with a PancakeSwap pair stored in pair. Normal buys, sells, and transfers route through _update(), which applies buy/sell/transfer fees unless either side is exempt. The Pancake pair address is also used by the token itself to decide whether a transfer is a buy or sell.

The dangerous design choice is that the sell-fee path is allowed to mutate the AMM pair's token balance and reserves. Constant-product AMMs assume their reserves move only through the pair's own mint/burn/swap/sync semantics; a token that burns from the pair and syncs during a sell lets a trader rewrite the reserve baseline immediately before a swap.

B. The Vulnerability

// contracts/phx.sol @ 0x2540CDc3317Aa614178c29e2a1C7d5cDcEBBa481
function _takeSellFee(address from, address to, uint256 amount) internal {
    uint256 opFee = amount * sellOperationFee / DENOMINATOR;
    uint256 lpFee = amount * sellLpFee / DENOMINATOR;
    uint256 fundFee = amount * sellFoundationFee / DENOMINATOR;
    uint256 burnFee = amount * sellBurnFee / DENOMINATOR;
    uint256 receiveAmount = amount - opFee - lpFee - fundFee - burnFee;

    uint256 pairBurnAmount = amount * sellPairBurnRate / DENOMINATOR;
    inFee = true;

    if (pairBurnAmount > 0) {
        uint256 pairBalance = balanceOf(pair);
        if (pairBurnAmount > pairBalance) {
            pairBurnAmount = pairBalance;
        }

        if (pairBurnAmount > 0) {
            _burn(pair, pairBurnAmount);
            IPancakePair(pair).sync();
            emit SellPairBurned(from, pairBurnAmount);
        }
    }

    super._update(from, operationWallet, opFee);
    super._update(from, lpWallet, lpFee);
    super._update(from, foundationWallet, fundFee);
    if (burnFee > 0) {
        _burn(from, burnFee);
    }
    super._update(from, to, receiveAmount);
    inFee = false;
}

This violates the AMM invariant by allowing a sell transfer to burn from pair and call sync() before the user's net sell amount is finally transferred to the pair.

C. Why It Was Exploitable

The precondition was a thin PHX side after the attacker bought nearly all PHX from the pair. Trace evidence shows the PHX/WBNB pair reserves before the first swap were 886,308.116609 PHX and 156.205783367 WBNB. The attacker then sent 467,555.488030 WBNB through PancakeSwap to buy 886,011.366875 PHX to an attack-controlled address, leaving only 296.749735 PHX in the pair.

A later PHX sell transfer of 593.499469 PHX triggered _takeSellFee(). Because sellPairBurnRate was 5000, the token burned 296.749735 PHX from the pair and called sync(), setting pair reserves to 1,000,000 raw PHX units and 467,711.693813 WBNB. The final net sell transfer then added ~504.474549 PHX to the pair, which was enough under the manipulated reserve baseline to withdraw 467,711.693713 WBNB.

III. Technical Attack Flow

  1. The EOA 0xf61FF6CD361561aC0274a7d3D197C79310bDEE61 deployed an attack wrapper, which created the executing contract 0x8D161cb068A576B53F5Be6f9f024B9c489e005f8 in the focal transaction.

  2. The attack contract flash-borrowed WBNB, BTCB, and USDT from 0x8F73b65B4caAf64FBA2aF91cC5D4a2A1318E5D8C. It also used Venus and an Aave-v3-style pool as temporary leverage sources; these loans were repaid in the same transaction and are not the vulnerable component.

  3. With temporary WBNB liquidity, the attack contract called Pancake Router swapTokensForExactTokens against the PHX/WBNB pair 0x09DBd035059b954d1D9c0076BDf6f70D2EFEB6CF. The router paid 467,555.488029525477661032 WBNB into the pair and received 886,011.366874573088068552 PHX out.

  4. The contract then invoked an unverified helper 0xB4a7E7cC2841725CdFFB5502C392c08D9433C217, which called PHX.transferFrom() to move 593.499469494402906536 PHX from the attacker EOA to the pair. This transfer hit PHX _takeSellFee().

  5. Inside PHX _takeSellFee(), the token burned 296.749734747201453268 PHX from the pair and called pair.sync(). Trace/state evidence shows the pair's PHX reserve changed to 1000000 raw units while its WBNB reserve stayed at 467,711.693812892500744808 WBNB.

  6. The final net PHX amount, 504.474549070242470556 PHX, arrived at the pair. The attack contract directly called pair.swap(0, 467711693712892500744808, attackerContract, ""), withdrawing 467,711.693712892500744808 WBNB and leaving only 0.0001 WBNB in the pair.

  7. The temporary Venus/Aave/flash-loan legs were unwound. The executing attack contract finished with 156.205683366923083775 WBNB and transferred that amount to the attacker EOA.
